# 101〜200位の苗字を追加する 設計書

作成日: 2026-08-14

## 1. 目的

現在の収録は全国1〜100位の100件のみで、それ以外の苗字を検索すると
「まだ収録されていません」で終わる。自分の苗字が101位以降にある利用者にとって、
このサイトは何も答えられていない。

101〜200位の苗字を、既存100件と同じ品質基準で追加し、検索でヒットするようにする。

## 2. スコープ

### やること

- 名字由来net の全国101〜200位の苗字を収録する
- 由来・全国順位・推定人口・都道府県分布・家紋・有名人を、既存と同じ基準で埋める
- `origin` の最低文字数を 100字 → 60字 に下げる
- データ品質を機械的に守るテストを3本追加する

### やらないこと

- **201位以降への拡張**（今回の範囲外）
- **解説のない「簡易エントリ」の新設**。中身の薄いページを量産しない
- 画面レイアウト・検索ロジック・デザインの変更
- ランキングページのページ送り（200行は1ページで許容範囲）

## 3. 収録方針

### 3.1 対象リストの基準

**名字由来net の全国ランキング101〜200位**（<https://myoji-yurai.net/prefectureRanking.htm>、
1〜500位が1ページに掲載されている）を対象リストとする。

既存の51〜100位も同じ基準で選定しており、詳細ページとランキングページには
「出典: 名字由来net。順位は参照元によって異なることがあります。」と既に明記してある。
この注記文はそのまま101位以降にも当てはまるので、文言の変更は不要。

name-power.net とは順位が最大で数位ずれるが、**両方を混ぜると「101〜200位」の集合自体が
定まらない**ため、対象リストの基準は名字由来net一本に固定する。
name-power.net は従来どおり、個々の苗字の裏取りソースとして使う。

### 3.2 品質基準は下げない

**「実際に fetch して本文を読んだ独立2ソースの一致のみ採用する」原則は据え置く。**
検索結果のスニペットは情報源ではない。媒体が違っても署名が同じなら1ソース。
有名人は1件ずつ本人のページを開いて確認する。裏が取れない項目は空にする。

101位以降は解説資料が薄くなるため、`origin` の最低文字数だけを **100字 → 60字** に下げる。

**これは「短くても書ける」ようにするための緩和であって、
「1ソースでも書いてよい」という緩和ではない。** 混同しないこと。

60字も書けない（＝2ソースで一致する由来が1つも見つからない）苗字は登録せず、
その順位は欠番にする。無理に埋めない。

既存100件の `origin` は変更しない。下限を下げても既存は全件100字を超えている。

### 3.3 空欄が増えることの想定

101位以降は家紋・有名人ともに資料が減る。既存100件でも家紋は70件が空である。
**空欄は失敗ではなく、裏が取れなかったという正しい記録である。**
埋めるための創作をしない。

### 3.4 slug の衝突

101〜200位には、読みが同じで字が違う苗字（渡部／渡邊など）が混ざる。
既存ルールをそのまま適用する。

> 最も一般的な字体が素の slug を取り、以降は区別する漢字の音読みを付す
> （斎藤=`saito` / 斉藤=`saito-sei`）

## 4. スキーマ変更

`src/lib/schema.ts` の1箇所のみ。

```diff
- origin: z.string().trim().min(100),
+ origin: z.string().trim().min(60),
```

既存100件は全件が100字超なので影響を受けない。

## 5. 検証構造

この案件では過去に「存在しないファイルを作成したと報告される」「テストが緑でも
そのテストが差を検出できない」という事故が起きている。100件を追加する作業では
同じことが再発する前提で、**先に機械的な網を張ってから**データ作成に入る。

### 5.1 追加するテスト

実測の結果、既存100件は全件が `sources` 4本以上・ホスト2種類以上だったので、
以下を追加しても既存データは1件も落ちない（追加時に実行して確認すること）。

| テスト | 内容 | 何を防ぐか |
|---|---|---|
| ソースの独立性 | `sources` が2本以上、かつ**異なるホストを2つ以上**含む | 同一サイト内の別ページを「2ソース」と言い張る経路 |
| 順位の一意性 | `rankNational` に重複がない | 順位の取り違え・コピペミス |
| origin 下限の固定 | 60字が通り、59字が弾かれる | 下限を無自覚に動かすこと |

**追加した各テストは、わざと壊して落ちることを確認する。**
「1件でも条件を満たせば通る」ようなアサーションを書かない。

### 5.2 作業の進め方

- **10件ずつ**作成し、各バッチの終わりに `npm test` を通す
- 各バッチの後、**ファイル数と登録済み順位を機械的に数えて**報告と実態を照合する
- 調査と執筆はコーディネーター自身が1件ずつ行う。
  過去に10件単位をサブエージェントへ委譲して1件も作られなかった事故があるため、
  このタスクは分割委譲しない
- 公開前に `npm run check:links` を手動で実行する。URL数は約2倍（1000本規模）になる

## 6. 画面への影響

変更なし。以下は自動的に追随する。

| 箇所 | 影響 |
|---|---|
| 検索 | インデックスが100→200件。数KBのままでクライアント内完結 |
| ランキング `/ranking` | 200行の1ページ。ページ送りは入れない |
| トップ `/` | TOP20 のまま変更なし |
| 静的ページ | 100→200枚。`generateStaticParams` が自動で生成 |
| フォント | 新出漢字ぶんサブセットが増える。`npm run build` が再生成し、完了時に実測値を報告する |

## 7. 完了条件

- 101〜200位のうち、2ソースで裏が取れたものがすべて登録されている
- 欠番がある場合、その順位と理由が報告されている
- `npm test` / `npm run typecheck` / `npm run lint` / `npm run build` がすべて通る
- `npm run check:links` に失敗がない
- 追加した3本のテストが、わざと壊すと落ちることを確認済み
